# /f - Fix Build (Автоматическое исправление ошибок сборки)

## Использование
```
/f [название проекта]
```

**Примеры:**
- `/f SNTP_API_Server` - исправить ошибки в API Server
- `/f SNTP_WordCollab` - исправить ошибки в Word Add-in
- `/f` - исправить ошибки во всём solution

---

## Назначение

Команда `/f` выполняет **автоматический цикл сборки и исправления ошибок** до полного успеха:

```
Build → Анализ ошибок → Исправление → Повтор до успеха
```

---

## Алгоритм работы

### Фаза 0: Инициализация VS2022

```
1. vs_list_instances → найти запущенные экземпляры VS2022
2. vs_select_instance solutionName: [название] → выбрать нужный
3. vs_get_debug_status → проверить текущий статус
```

**Если VS2022 не запущен:**
```
⚠️ Visual Studio 2022 не найден. Запустите solution и повторите команду.
```

---

### Фаза 1: Сборка проекта

```
1. vs_build_solution → компиляция
2. vs_get_build_errors → получить список ошибок
```

**Если ошибок нет:**
```
✅ Сборка успешна! Ошибок не обнаружено.
```
→ Завершить выполнение

---

### Фаза 2: Классификация ошибок

Для каждой ошибки определить тип:

| Тип ошибки | Признаки | Действие |
|------------|----------|----------|
| **Синтаксическая** | CS1002, CS1026, BC30035 | Исправить синтаксис |
| **Отсутствует тип/член** | CS0246, CS0103, BC30002 | Добавить using/import или создать |
| **Несовместимость типов** | CS0029, CS1503, BC30311 | Привести типы |
| **Дублирование** | CS0111, CS0102, BC30260 | Анализ → удаление/рефакторинг |
| **Неоднозначность** | CS0121, CS0104, BC30521 | Уточнить namespace |
| **Устаревший API** | CS0618, CS0619 | Обновить вызов |
| **Отсутствует файл** | CS2001, BC30451 | Создать или удалить ссылку |

---

### Фаза 3: Исправление ошибок

#### 3.1. Для каждой ошибки:

```
1. Read: [файл с ошибкой] → прочитать контекст
2. Определить причину ошибки
3. Применить исправление (Edit/StrReplace)
```

#### 3.2. При дублировании (CS0111, CS0102, BC30260):

**Алгоритм анализа дублирования:**

```markdown
## Анализ дублирования: [ИмяКласса/Метода]

### Шаг 1: Найти все определения
Grep: pattern:"(Class|Function|Sub|Public|Private)\s+[ИмяЭлемента]"

### Шаг 2: Прочитать документацию
Read: #memory\[модуль]=[файл]=_global_.MD
Read: #memory\[модуль]=[файл]=[функция].MD

### Шаг 3: Сравнить функционал

| Критерий | Определение 1 | Определение 2 |
|----------|---------------|---------------|
| Файл | path/file1.vb | path/file2.vb |
| Назначение | [из документации] | [из документации] |
| Параметры | [сигнатура] | [сигнатура] |
| Зависимости | [кто вызывает] | [кто вызывает] |

### Шаг 4: Решение

**Вариант A: Истинное дублирование** (одинаковый функционал)
→ Удалить одно из определений
→ Обновить все вызовы

**Вариант B: Совпадение имён** (разный функционал)
→ Переименовать один из элементов
→ Обновить документацию
```

#### 3.3. При несовместимости функции:

```markdown
## Анализ несовместимости: [ИмяФункции]

### Шаг 1: Определить контекст вызова
- Откуда вызывается?
- Какие параметры передаются?
- Какой результат ожидается?

### Шаг 2: Проверить документацию
Read: #memory\[модуль]=[файл]=[функция].MD

### Шаг 3: Варианты решения

**A. Адаптировать вызов** под существующую сигнатуру
**B. Добавить перегрузку** с нужной сигнатурой
**C. Рефакторинг функции** под новые требования
```

---

### Фаза 4: Повторная сборка

```
1. vs_build_solution → повторная компиляция
2. vs_get_build_errors → проверить результат
```

**Если ошибки остались:**
→ Вернуться к Фазе 2 (следующая итерация)

**Если ошибок нет:**
→ Перейти к Фазе 5

**Защита от бесконечного цикла:**
- Максимум 10 итераций
- Если ошибка повторяется 3 раза → запросить помощь пользователя

---

### Фаза 5: Верификация и оптимизация

После успешной сборки:

```markdown
## 5.1. Проверка warnings

vs_get_build_errors includeWarnings: true

Для каждого warning оценить:
- Критичность (может ли стать ошибкой?)
- Простота исправления
- Влияние на качество кода

Исправить warnings с высоким приоритетом.
```

```markdown
## 5.2. Анализ внесённых изменений

Для каждого изменённого файла:
1. Проверить согласованность с документацией #memory
2. Обновить @changelog в JSDoc/XML-комментариях (если применимо)
3. Проверить отсутствие регрессий (связанные функции)
```

```markdown
## 5.3. Оптимизация (опционально)

Если в процессе исправления обнаружены:
- Неиспользуемые using/imports → удалить
- Дублирующийся код → предложить рефакторинг
- Устаревшие конструкции → предложить модернизацию
```

## Обработка сложных случаев

### Конфликт имён с разным функционалом

```markdown
## Конфликт: [ИмяЭлемента]

**Определение 1:** `ModuleA/FileA.vb`
- Назначение: [описание из документации/кода]
- Используется в: [список вызывающих]

**Определение 2:** `ModuleB/FileB.vb`
- Назначение: [описание из документации/кода]
- Используется в: [список вызывающих]

**Решение:** Переименование

| Было | Стало | Обоснование |
|------|-------|-------------|
| ModuleA.Process() | ModuleA.ProcessData() | Более специфичное имя |
| ModuleB.Process() | ModuleB.ProcessRequest() | Отражает назначение |

**Обновлены вызовы в:**
- File1.vb:23
- File2.vb:45
```

### Циклическая зависимость

```markdown
## Циклическая зависимость

**Обнаружено:**
ModuleA → ModuleB → ModuleC → ModuleA

**Решение:**
1. Выделить общий интерфейс в отдельный модуль
2. Использовать Dependency Injection
3. Реорганизовать архитектуру
```

### Отсутствующая зависимость (NuGet)

```markdown
## Отсутствует пакет: [PackageName]

**Действия:**
1. Проверить packages.config / .csproj
2. Восстановить пакеты: `nuget restore`
3. Если пакет удалён намеренно → удалить использование
```

---

## Важные принципы

1. **Не ломать работающий код** — анализ перед удалением
2. **Документация = истина** — сверка с #memory перед решением о дублировании
3. **Минимум изменений** — исправлять только то, что вызывает ошибку
4. **Сохранять функционал** — при рефакторинге не терять возможности
5. **Итеративность** — одна проблема за раз, повторная сборка после каждого исправления
