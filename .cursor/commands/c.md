# /c — Критический разбор

> **Прими или опровергни. Придумай. Улучши. Оптимизируй.** - Это твоя директива к действию.

## Шаг 1. Зафиксируй объект разбора

Одним предложением сформулируй, что именно оцениваешь (утверждение, архитектурное
решение, кусок кода, план). Если объект неясен или их несколько — разбери каждый отдельно.

## Шаг 2. Собери доказательства

- **Код проекта:** если идея касается существующего кода — прочитай его (и `#memory`-документацию
  модуля), не оценивай по памяти.
- **Интернет:** выполни 2–3 поисковых запроса (best practices, известные проблемы,
  альтернативные подходы) с привязкой к стеку VB.NET / SQL Server / JavaScript.
  При необходимости открой 1–2 источника целиком.
  **Пропусти поиск**, если вопрос чисто внутренний (логика конкретной функции проекта,
  договорённости в кодовой базе) и интернет ничего не добавит — но тогда напиши, что поиск
  пропущен и почему.

## Шаг 3. Вердикт — первой строкой ответа

`✅ Принимаю` / `❌ Опровергаю` / `⚠️ Принимаю частично: <что именно>`

Ниже — аргументы по существу: факты из кода, найденное в интернете, ограничения стека.
Если опровергаешь — покажи конкретное место, где ломается логика. Общие слова
(«это хорошая практика») без опоры на шаги 1–2 аргументом не считаются.

## Шаг 4. Варианты и сравнение

Если существуют осмысленные альтернативы (включая исходную идею) — сравни их таблицей:

| Критерий | Исходная идея | Вариант B | Вариант C |
|---|---|---|---|
| Решает задачу полностью | | | |
| Сложность реализации в нашем коде | | | |
| Производительность | | | |
| Поддерживаемость | | | |
| Совместимость со стеком (VB.NET/SQL/JS) | | | |

После таблицы — выбор одним предложением и почему. Максимум 3 варианта.
Если реальной альтернативы нет — напиши «альтернатив, лучших по существу, не нашёл»
и не выдумывай варианты ради таблицы.

## Шаг 5. Улучши и оптимизируй выбранный вариант

- Точечные улучшения: что изменить, в каком месте, почему. Без абстракций вида
  «добавить обработку ошибок» — только с привязкой к конкретному месту.
- Оптимизация = прежде всего упрощение: что убрать как лишнее, где узкое место.
  Не предлагай усложнений без измеримой выгоды.
- Риски и слабые места выбранного варианта — указать всегда, с митигацией в одну строку.

## Правила честности (перекрывают всё выше)

- «Принимаю, улучшений не требуется» — полноценный и допустимый итог.
- Не хватает данных для вердикта — назови, каких именно, вместо гадания.
- Не подгоняй сравнение под заранее выбранный ответ: если поиск/код опровергли
  первоначальное впечатление — так и напиши.
- Ответ компактный: вердикт и выбор варианта — обязательны, остальное только по делу.
  Это разбор, а не реализация: код не менять, пока пользователь не подтвердит.
